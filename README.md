## 1. 项目简介

「小书」是替代人工客服**初步沟通环节**的 AI 客服系统：通过 AI 对话收集家政服务需求（住家 / 白班 / 育儿 / 养老护工 / 钟点 / 菲式 6 类保姆），并在对话中处理高频问题（中介费、阿姨工资、转人工等）。

客户从**广告落地页**点进来，目的通常是"找阿姨"，但还处在了解和评估阶段。此时出现的高频问题有明显的边界：**预约面试、换人售后、合同签约**这类流程靠后的动作，在售前聊天里概率很低，不值得现在加——加了反而会稀释分类器的注意力、增加误判率。

## 3. 总体架构 —— 三层路由

```
客户消息
    │
    ▼
┌─────────────────────────────────────────────────────────┐
│  L1 正则层（代码内，毫秒级，0 次 LLM 调用）                  │
│  · fee_info 4 别称命中 → 直出中介费模板（不收取）          │
│  · FAQ 触发词命中 → 直出已审核标准文本（内容货架）            │
└────────────────────────────┬────────────────────────────┘
                     未命中 ↓
┌─────────────────────────────────────────────────────────┐
│  L2 意图分类（妙搭「意图分类器-L2」独立实例，只判不说）       │
│  4 值枚举：transfer_human / market_price /               │
│           service_scope / none                           │
│  后端五步校验 + 置信度阈值 0.7                              │
└────────────────────────────┬────────────────────────────┘
    命中(≥0.7) ↓                        none / 低于阈值 ↓
┌───────────────────┐        ┌────────────────────────────┐
│ 触发工具/模板      │        │  L3 客服实例（主对话通道）        │
│ · 转人工 / 查花费  │        │  · 大模型回复 + 需求采集        │
│ · 答职责清单       │        │  · 输出含 [[FIELDS]] 数据     │
└───────────────────┘        └────────────────────────────┘
                                       │ 提取字段
                                       ▼
                        normalizer 归一化 → 三层存储（只存变化）
```

**核心流程：** 客户消息 → L1 扫关键词（毫秒级、稳）→ 没抓到 → L2 大模型理解意图（泛化强，但有不确定性，用 none + 置信度锁死）→ 也没抓到 → L3 主对话通道（大模型回复 + 边聊边提取需求，用 `[[FIELDS]]` 标记符夹带数据）→ 字段过 normalizer 归一化 → 三层存储只存变化（完整链路图见文末【项目全景流程】）。

> L3 是主对话通道——绝大多数日常对话都走这里，不是"都没听懂才启用"的兜底。

## 4. 意图体系

### 4.1 总览：谁在哪个层

| 意图 / 主题          | 所在层         | 类型       | 触发后做什么                                  |
| ---------------- | ----------- | -------- | --------------------------------------- |
| `fee_info`（中介费）  | **L1 正则直出** | 动作型（查价）  | 查常量 → 套模板 → 落日志                         |
| `transfer_human` | L2 分类       | 动作型（切流程） | 切人工模式 + 发通知 + 留资                        |
| `market_price`   | L2 分类       | 动作型（查花费） | 查价格数据 → 套「总花费」模板（总花费 = 工资行情 = 总预算，无中介费） |
| `service_scope`  | L2 分类       | 动作型（答清单） | 直答"阿姨负责做饭/清洁/照顾…"                       |
| `none`           | L2 分类       | 兜底       | 放行 L3（含需求描述 / FAQ 类 / 含糊费用问法 / 闲聊）      |
| FAQ 001~007      | FAQ 货架      | 内容型      | 查表回已审核文本                                |

> L2 的 3 个真意图全是动作型（转人工 / 查花费 / 答职责清单）——触发后执行动作，不存在"反问澄清"型意图。fee_info 不在 L2 枚举里（L2 只有 4 值），由 L1 正则全权处理。

### 4.2 L1 正则层（fee_info + FAQ）

**根事实：公司不向客户收取中介费（中介费 = 0，业务确认）。**"服务费 / 信息费 / 介绍费"一律按中介费别称处理，直出"不收取、按预算/市场行情匹配"模板。

```
客户耳朵里 → 触发词宽：/（中介费|服务费|信息费|介绍费）/ → fee_info
代码手里  → 动作窄：只查中介费一张表、只套一个模板
```

**fee_info 工具流程（L1 命中即走，不进 L2）：**

1. **归一化**：用户原词（如"服务费"）→ 映射回"中介费"
2. **读常量**：`INTERMEDIARY_FEE = 0`（不收取，无地区差异，无需查库）
3. **套模板**：固定文案"我们这边是不收阿姨费用的，所以一般是按咱们的预算或市场价匹配"
4. **落日志**：费用类话题留痕（每次命中记日志，不可省）

**FAQ 触发词命中（L1 直出）：** L1 判定 fee_info 之外，再判一遍 FAQ 触发词 → 命中即查 `faqs` 表回标准文本（内容货架，不进 L2）。

**L1 位置还有三类毫秒级关键词检测（框图未画，机制详见 §5.7）：** 实际执行时，以下检测同样排在 L2/L3 之前、0 次 LLM 调用——① **转人工关键词**（"找人工"等，命中即切人工）；② **情绪升级关键词**（不耐烦 → 宁可误转）；③ **月休非标早拦截**（"月休 6 天"等 → 直接模板回复）。它们在 §5.7 按"转接触发职能"归类讲述。

**边界分流（涉费敏感话题）：**

| 用户原话                         | 真实意图                                 | 路由                                                           |
| ---------------------------- | ------------------------------------ | ------------------------------------------------------------ |
| 中介费 / 服务费 / 信息费 / 介绍费        | 问公司单项收费                              | **fee_info（L1 直出"不收取"）**                                     |
| 阿姨一个月多少钱 / 阿姨工资多少            | 问请阿姨的花费——**工资词也是问总账**（无中介费，总花费 = 工资） | **market_price（答总花费：工资行情 = 总预算）**                            |
| 请个住家保姆总共多少钱 / 一共要花多少（带类型）    | 问请阿姨的总花费（同一本账）                       | **market_price（答总花费）**                                       |
| 保姆总共多少钱 / 全部算下来（泛称）          | 问总花费（泛称）                             | **market_price**（工具层看类型缺失走泛称兜底：给总范围 / 反问想找哪类，**不按猜测单类报价**）   |
| 你们怎么收费 / 收费模式（模糊钱问法，无明确费用对象） | 默认当问总花费                              | **market_price（默认答总花费；客户澄清"我问的是中介费" → L1 fee_info 直出"不收取"）** |
| 中介费能便宜吗 / 能退吗                | 砍价 / 售后                              | **transfer_human**                                           |
| 能换人吗 / 服务保障有哪些               | 看政策                                  | **FAQ-003**                                                  |
| 怎么付款 / 能分期吗                  | 付款流程                                 | FAQ-006（暂不做）                                                 |
| 孤零零一句"费用多少 / 多少钱"（无对象无上下文）   | 模糊钱问法（默认当问总花费）                       | **market_price（默认答总花费，不反问；客户澄清指向中介费 → L1 fee_info）**         |

> 最容易错的对照：**"中介费多少钱" → fee_info（L1 直出）** ｜ **"阿姨一个月多少钱" → market_price** ｜ **"请住家保姆总共多少钱" → market_price（同一本账）** ｜ **"你们怎么收费" / 孤零零"费用多少"（模糊钱问法） → 默认 market_price 按总账答**。所有 market_price 问法都不反问，统一按总账答——客户口中无论"工资 / 月薪 / 多少钱一个月 / 总共多少 / 收费模糊问法"，先按同一笔总花费答（= 工资行情，无中介费差额）；客户明确说"我问的是中介费"时，句中含费用词 → L1 fee_info 直出"不收取"。

**工具/模板直出要点：** 命中规则后，不经过 AI 生成，直接从数据库拿预先写好的固定回复模板发出去（比如中介费模板）。又快又稳。

> 校验器作用域：受控模板反而豁免——它只查 L3 大模型回复，不查 L1/L2 模板（详见 §4.5）。

### 4.3 L2 意图分类（4 值枚举）

| 值                | 一句话边界                                                                    | 关键正例 / 反例                                        |
| ---------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| `transfer_human` | 明确要真人 / 投诉 / 要电话 / 要求线下                                                  | "我要找真人客服聊" / "能投诉吗"                              |
| `market_price`   | 问**请阿姨要花多少钱**（含模糊钱问法"你们怎么收费 / 费用多少"）：一律按**一本总账**答（总花费 = 工资行情 = 总预算，无中介费） | "住家保姆一个月多少钱" / "请个住家保姆总共多少钱" / "你们怎么收费"（模糊默认按总账） |
| `service_scope`  | 问**阿姨做什么**（职责范围）                                                         | "阿姨都负责做哪些事"                                      |
| `none`           | 需求描述 / FAQ 类 / 闲聊 / **fee_info 4 别称**（L1 已截走，LLM 不该见到）                   | "我想找住家阿姨带娃" / "中介费怎么收"（实为 L1 截走）                 |

**『钱』类问法判别（4 值版铁律）：**

- 句中含 4 个别称 → 归 L1（fee_info）截走，L2 判 **none**
- 问"请阿姨要花多少钱"——客户用"XX 保姆一个月多少钱 / 月薪 / 工资多少"或"总共 / 一共多少钱"都一样 → **market_price**。客户看的是**一本总账**：**总花费 = 工资行情 = 客户的总预算**（不收中介费，无差额）。报价只有这一种口径，**不反问"你问的是工资还是中介费"**
- 问"公司/平台怎么收费、费用多少、收费模式/收费规则是什么样的、还有别的费用吗"等**一切收费类问法**（无明确费用对象）→ **默认 market_price**：按总花费直答（总花费 = 工资行情），不反问、不区分问法；客户澄清"我问的是中介费"时句中含费用词 → L1 fee_info 直出
- 孤零零一个"费用/多少钱"，前后文都看不出问什么 → **market_price**（模糊钱问法默认按总账答，不反问；见上条）

**为什么花钱问法只按一本总账答、不问口径：**

> 业务事实是：**客户只关心自己要付的总价**——阿姨工资多少是拆分视角，客户不关心；且**公司不收客户中介费（= 0）**，总价与工资是同一个数。既然客户看的是同一本总账，反问"您问的是公司收费还是阿姨工资"对客户没有意义。  
> 保守落点 = "**能答才答、答不了放行 L3**"：请阿姨的花费问法**以及全部收费类问法**（"你们怎么收费/费用多少/收费模式/还有别的费用吗"）一律直答总花费（总花费 = 工资行情，不会错）；客户明确点名中介费 → L1 fee_info 直出"不收取"；啥都说不清的判 none 交 L3 人话兜底。

**规则要点：**

- 需求描述一律 none，别截胡（那是阶段一采集的活）
- confidence < 0.5 ≈ 在猜 → 判 none
- 后端阈值 0.7：有意图但置信度不够 → 放行 L3，绝不硬触发

**调用实现（L2 五步，一道不能省）：**

调用点：L1 未命中之后、L3 回复之前。`fee_info` 不在此处出现（归 L1 正则处理）。以下是流程示意，不是实际代码：

```typescript
const THRESHOLD = 0.7;
const INTENTS = ['transfer_human', 'market_price', 'service_scope', 'none'];
// fee_info 不在 INTENTS 里（归 L1 正则处理）

async function l2Classify(messageId: string, userMsg: string, recentRounds: string[]) {
  // 第 1 步：独立调用分类实例（只传当前句 + 最近 2~3 轮）
  const raw = await callClassifierInstance(userMsg, recentRounds);
  // 第 2 步：解析。失败 → 记日志 + 当 none 放行 L3（不许静默丢）
  let parsed; try { parsed = JSON.parse(raw); } catch { logger.warn(...); return none; }
  // 第 3 步：白名单校验 —— intent 不在 4 值里？当 none
  if (!INTENTS.includes(parsed.intent)) { logger.warn(...); return none; }
  // 第 4 步：none 直接放行；有意图但置信度 < 0.7 → 放行，绝不硬触发
  if (parsed.intent === 'none' || confidence < THRESHOLD) return { intent, hit: false };
  // 第 5 步：高置信命中 → 触发工具/模板 + 存学习样本（走到这 = L1 没抓到，即正则缺口）
  triggerTool(intent, userMsg);
  saveLearningSample({ messageId, intent, confidence, l1Missed: true });
}
```

**L2 语义检测要点：** LLM 读客户这句话判断属于哪个意图，靠"理解意思"而非"扫关键词"（L1 不认识"你们靠不靠谱啊"，L2 能听懂这是试探信誉 → 判 none 不硬猜）。AI 只能从 4 个值选 1 + `JSON.parse` 直接解析（不能输出散文）。置信度 0~1，低于阈值 0.7 → 放行 L3，绝不猜（防止"蒙对意图但答案是编的"）。解析失败 / 不在枚举里 → 一律当 none 处理（最后兜底）。

**FAQ vs 意图判据（4 行）：**

| 维度    | 意图（Intent）                       | FAQ                     |
| ----- | -------------------------------- | ----------------------- |
| 本质    | 行为岔路口（做动作 / 查数据 / 转人工）           | 内容货架（展示标准文本）            |

### 4.6 预算口径

**业务口径：客户报的预算 = 总价 = 阿姨工资**（公司不收客户中介费，无差额）。**全系统只有一个对客金额口径 = 总预算（总花费）**：需求采集只采它，market_price 报价也只答它（见 §4.3）；顾问匹配直接用预算值即可。

**定稿决策：**

1. **预算字段已存在，存的口径就是总价** → 不迁移、不新增"抄原数"字段
2. **对客红线：不主动提中介费，客户没问就不提**。只有客户主动问起（"要中介费吗 / 有别的费用吗"）才如实说明：不收客户中介费，阿姨按预算/市场行情匹配
3. **口径纯一刀切**：不做"工资口径 / 总价口径 / 含糊"的分类教学、**也不做例外识别**。**客户报的任何一个金额，一律当总价直接写进预算字段**——"就 6000 吧"这种干数字按总价记，"每月付给阿姨工资 5500"也原样记 5500：不追问口径、不引导补报。
   - **为什么无偏差**：中介费为 0，总价与工资是同一个数——客户报的数不管是"工资视角"还是"总价视角"，落库值都一样，一刀切**零代价**。
   - **为什么一刀切**：客户只关心自己要付的总账、不关心拆分视角，让 AI 去猜"这是工资还是总价"只会徒增错判面。
4. **无需派生函数**：预算 = 工资，顾问后台直接展示预算值用于匹配，不做任何加减换算。

**AI 红线（写进 L3 prompt）：** 不做口径判断与引导——客户报任何数一律当总价直抄进预算字段（明说"给阿姨工资 X"也不例外，因为无差额）｜不承诺"这预算能请到 XX"。

**收费口径兜底**：若费用问法绕过 L1 正则和 L2 分类（罕见漏网），L3 客服实例也不许自由发挥——客户问到收费/中介费等，固定用定稿文案"我们这边是不收阿姨费用的，所以一般是按咱们的预算或市场价匹配"作答；不编造金额、不主动提费用字眼。这样即使三层全漏，收费口径也话术可控。

### 5.4 特殊规则

**1. service_type 枚举值（必须统一）+ 非标准说法先确认：** `住家保姆、白班保姆、钟点工保姆、育儿保姆、护工保姆、菲式保姆`。禁止输出拼音、禁止中英文混杂；含标准类型词的表述（如"住家阿姨"）可直接归一。**客户用非标准说法（"阿姨""保姆""育儿嫂""养老保姆""护工""带娃""照顾老人"）时，AI 不直接归一到最接近的标准值**——先用一句话重新申明最可能的标准类型及其主要职责、向客户确认（例："您是想找育儿保姆吗？主要负责宝宝的喂养和日常护理"），客户确认后才写入该类型；否认则按纠正采集。养老相关需求确认后统一归「护工保姆」。

**2. service_hours 适用规则：** 钟点工保姆必问（核心字段）；育儿/护工/菲式主动问；住家/白班不问用默认值（住家=24 小时，白班=8~9 小时）。

**3. rest_days 选项规则：** 钟点工保姆：无月休 / 月休 2 天 / 月休 4 天（3 选 1）；其他类型（住家/白班/育儿/护工/菲式）：月休 2 天 / 月休 4 天（2 选 1）；特殊情况（月休 1 天、6 天等）→ 转人工沟通。

**4. 提取优先级 = 老值优先（双路径统一）：** 实时正则命中即写库（新值覆盖，正则确定性高）；AI 全量提取按字段 merge，已存值优先、AI 新值填空——AI 抽错的字段不覆盖已存正确值（如客户前 3 轮说"住家 7000 元"，AI 第 4 轮抽成"白班 6500 元"，老的"住家 7000"留下来）。**代价**：客户真改口 AI 不自动更新，必须由顾问后台手动修正兜底（"老值优先 + 改口人工"是一对绑定口径）。

**5. 状态机单调性（防 AI 误判回退）：** requirements.status 只进不退——`pending → collecting → completed` 单调递增；AI 每轮全量提取不应把 `completed` 判回 `collecting`（否则后台误以为采集被回退，可能误触派单 / 通知 / 转人工）。leads.status 同口径（仅 `new/pending → collected`，**不进 `completed`**——leads 端的完成语义要等人工确认）。

### 5.5 AI 输出增强格式（value / status / confidence / source）

每个字段不仅输出值，还输出 status（明确/模糊/无值）和 confidence（置信度）：

```json
{
  "value": "不需要",
  "status": "clear",
  "confidence": 0.95,
  "source": "客户明确表示家里没有老人需要照顾"
}
```

| 维度             | 含义          | 取值                   |
| -------------- | ----------- | -------------------- |
| **value**      | 字段的值        | 字符串                  |
| **status**     | 客户回答的明确程度   | clear / vague / none |
| **confidence** | AI 对判断的把握程度 | 0.0 ~ 1.0            |
| **source**     | 从哪句话提取的     | 原文引用                 |

**处理逻辑：** status = none → 无值跳过 ｜ status = clear 或 vague → 进入下一步 ｜ confidence ≥ 0.5 → 写入数据库 ｜ confidence < 0.5 → 低置信跳过不存。status 和 confidence 是"过程数据"，判断完就丢，目前不存库。

> ⚠️ 此处 0.5 是**字段提取的写入门槛**（代码 `MIN_FIELD_CONFIDENCE = 0.5`，判断"这个字段值够不够确定、能不能写库"），与 §4.3 L2 意图路由的 0.7 采信线是**两回事**，不要混用。

> **格式的唯一出处 = `[[FIELDS]]` 指令**：上表 4 个维度的定义 + 四条提取铁律（提取＝摘录 / 通用清洗 / 状态判断 / 只填确定的）**全部由 `buildFieldsOutputInstruction()` 每轮动态拼接**（`chat.prompt.ts:795-894`，随 `collected_requirements` 送进 L3）。改格式只改这一处。

### 5.6 [[FIELDS]] 解析加固三步

1. **先抠标记再 parse**：从整段 AI 回复里用正则把 `[[FIELDS]]` 和 `[[/FIELDS]]` 之间内容抠出来，再 `JSON.parse`。AI 在标记外说废话也不影响。
2. **失败记日志**：以前 parse 失败静默丢掉（不知道哪条消息数据丢了），现在失败要记一条错误日志，方便排查。
3. **字段白名单**：解析出的 JSON 只认定义过的字段名，AI 自己发明的字段一概丢弃，防脏数据进库。

### 5.7 护栏机制

**已采集字段剥离（stripReask）：** AI 提问时，已经采集到的字段（status = clear）不能再问，避免重复提问引起客户反感。vague 字段可以自然确认，但不能像没采集过一样直接问。

**transferReason 业务化文案：**

| 底层原因（7 种）              | 客服侧展示（6 种）               |
| ---------------------- | ------------------------ |
| 需求采集完成                 | 需求采集完成                   |
| 客户消息含转人工关键词            | 客户申请转人工                  |
| 情绪升级                   | 情绪升级                     |
| AI 主动申请转接（transfer 标签） | AI 主动申请转接（AI 处理不了）       |
| AI 话术关键词兜底             | *归入 AI 主动申请转接这类，技术细节不暴露* |
| 客服超时未响应                | 客服超时未响应                  |
| 客服手动转接                 | 客服手动转接                   |

**转人工触发判定（触发顺序 + 幂等守卫 + 谁先命中谁写原因）：** 触发顺序固定，从高到低——① 字段全齐了吗？→"需求采集完成"；② 客户说转人工？→"客户申请转人工"；③ 情绪超阈值？→"情绪升级"；④ AI 输出 transfer 标签？→"AI 主动申请转接"；⑤ AI 回复含转人工关键词？→"AI 主动申请转接"。**第一个命中的就确定 reason**，后面条件即使也命中也不会覆盖。**幂等守卫：** 一旦 mode 被切到 human，后续所有触发路径直接跳过，不重复执行、不改 reason。**兜底路径命中条件：** 仅当 AI 自己决定要转人工（该业务情况 AI 处理不了），但忘了输出 transfer 标签、只在话里说了。

### 5.8 normalizer 归一化 + 三层存储

**normalizer 归一化：** 提取出的字段值做规范化——"川妹子 → 四川"、"一百二十平 → 120"；单位换算（平方米/平）、别名映射（方言/俗称 → 标准）。**写死的映射表 / 单位换算为准，不依赖 AI**（避免 AI 每次换说法）。

**三层存储（只存变化，不做全量快照）：**

1. **消息表**：客户原话（source 用 message_id 引用，不复制）
2. **现值表**：每个字段当前最新值（union 合并，只存变化）
3. **delta 日志**：字段值的变更记录（审计 / 回溯）

## 6. 飞书互动卡片嵌入对话方案

### 6.1 整体思路

**卡片 + 对话混合采集模式：** **卡片**采集客观事实字段（几口人、面积、宠物、月休等）——客户不用想，直接选/填；**对话**采集主观字段（阿姨要求、做饭口味、薪资预算）——AI 引导追问，深度沟通。卡片作为一条消息出现在对话流里，客户填表提交后，AI 自动接着聊剩余字段。

### 6.2 完整对话流程

```
小书：您好，您选择的是【住家保姆】，先填一下基本信息吧：
      [卡片：住家保姆需求采集]
客户：[填表 → 提交]
小书：收到啦～ 我再跟您确认几个细节：
      对阿姨有什么要求吗？比如年龄、经验...
```

### 6.3 技术架构

```
客户对话 → Bot 发送卡片 → 客户填写提交 → 飞书回调后端
                                            ↓
                                       校验签名 + 幂等
                                            ↓
                                       解析表单数据 → 写入 DB
                                            ↓
                                       触发 AI 继续对话
                                            ↓
                                  AI 读取已采字段，接着聊
```

### 6.4 住家保姆卡片字段（8 个）

| 分组     | 字段        | 组件类型                      | 必填   |
| ------ | --------- | ------------------------- | ---- |
| 家庭基本情况 | 几口人吃饭     | 输入框                       | ✅    |
| 家庭基本情况 | 房屋面积      | 输入框                       | ✅    |
| 家庭基本情况 | 是否有宠物     | 下拉选择                      | ✅    |
| 照护需求   | 需要照顾老人    | 勾选 + 详情下拉                 | 条件必填 |
| 照护需求   | 需要照顾/接送小孩 | 勾选 + 详情下拉                 | 条件必填 |
| 工作安排   | 月休几天      | 下拉选择                      | ⭕    |
| 工作安排   | 到岗时间      | 下拉选择（尽快/一周内/两周内/一个月内/不确定） | ✅    |
| 工作安排   | 服务地址      | 输入框                       | ✅    |

> 阿姨要求、做饭口味、**薪资预算** → 走对话采集，不在卡片里。

### 6.5 卡片回调处理要点

1. **签名校验**：验证飞书回调请求合法性
2. **幂等性**：event_id 去重，防重复提交
3. **数据校验**：必填字段 + 条件必填（勾选老人/小孩 → 详情必填）
4. **字段映射**：卡片枚举值 → 数据库中文描述
5. **写入 DB**：更新 requirement 记录，标记 source=card
6. **触发 AI**：异步触发 AI 继续对话

### 6.6 边缘情况

| 场景         | 处理方式                       |
| ---------- | -------------------------- |
| 客户提前回答部分字段 | 卡片提交值覆盖对话值（以最终提交为准）        |
| 客户重复提交卡片   | 按 requirement_id 更新，不创建新记录 |
| 客户不填卡片直接打字 | AI 正常走对话采集，忽略卡片            |
| 卡片发送失败     | AI 降级为纯对话模式                |
| 客户填了没点提交   | AI 后续检测到字段未采齐时，用对话补问       |

### 6.7 数据库变更

```sql
-- 需求来源：card / chat / mixed
ALTER TABLE requirements ADD COLUMN IF NOT EXISTS source text DEFAULT 'chat';
-- 卡片提交时间
ALTER TABLE requirements ADD COLUMN IF NOT EXISTS card_submitted_at timestamp;
```

## 7. 线索分级与派单排序（预算口径 = 总价）

### 7.1 线索分级（6 档）

| 档位          | 含义       | 触发条件                            | 响应时限         | 是否分配人工        |
| ----------- | -------- | ------------------------------- | ------------ | ------------- |
| **A**       | 优质线索     | AI 走完采集 + 三维度评分 ≥ 6 分 + 预算不严重偏离 | 2 分钟         | ✅             |
| **B**       | 普通线索     | AI 走完采集 + 三维度评分 < 6 分 + 预算不严重偏离 | 5 分钟         | ✅             |
| **B-price** | 预算偏低线索   | AI 走完采集 + 预算严重偏离（低于偏低价区间）       | —            | ❌（AI 培育，不转人工） |
| **C1**      | 客户主动转人工  | AI 未走完采集，客户主动要求转人工              | 按情绪分级（见 7.3） | ✅             |
| **C2**      | 待采集线索    | AI 未走完采集 + 客户沉默                 | —            | ❌（AI 继续采集）    |
| **D**       | 黑名单 / 无效 | 号码异常、行为异常                       | —            | ❌（直接丢弃）       |

> 🎯 **AI 走完采集后能确定填值的字段才填，确定不了的标"待定"**。（字段数以 §5.1 的 15 个采集字段为准。）

### 7.2 A/B 档判定与排序规则

AI 走完采集后，按三个维度打分（每项 1–3 分），总分 ≥ 6 分 = A 档，< 6 分 = B 档：

| 维度        | 1 分                               | 2 分            | 3 分           |
| --------- | --------------------------------- | -------------- | ------------- |
| **预算匹配度** | 严重偏离（低于偏低价区间）→ B-price（AI 培育不转人工） | 中匹配（落在偏低价区间内）  | 高匹配（落在正常价区间内） |
| **时间紧迫度** | 一个月以上 / 不确定                       | 两周内            | 一周内 / 尽快      |
| **需求明确度** | < 60% 字段有明确值（其余待定）                | 60%–80% 字段有明确值 | > 80% 字段有明确值  |

**举例：** 高预算(3)+一周内(3)+90%字段明确(3)=**9 分→A**；中预算(2)+两周内(2)+70%(2)=**6 分→A**（刚好过线）；高预算(3)+一个月后(1)+90%(3)=**7 分→A**（不急但优质）；中预算(2)+一个月后(1)+70%(2)=**5 分→B**。**同档位排序：** 按三维度总分从高到低，分数相同则先来后到。

### 7.3 C1 档内排序规则（按情绪分级）

| 情绪等级      | 判定             | 响应时限 | 说明                    |
| --------- | -------------- | ---- | --------------------- |
| **高优先级**  | 愤怒 / 投诉 / 急切催促 | 2 分钟 | 客户情绪激动或很着急，优先处理防流失/升级 |
| **普通优先级** | 简单求助 / 礼貌询问    | 5 分钟 | 情绪平稳，正常排队             |

**AI 情绪判断依据：** 分析客户最后 1–3 条消息的用词和语气。关键词——愤怒/投诉：投诉、垃圾、什么玩意、太差了、骗人、退款、差评；急切催促：赶紧、立刻、马上、怎么还没人、等多久了、太慢了；简单求助：帮我、问一下、咨询一下、了解一下；礼貌询问：您好、请问、麻烦问下、方便吗。

### 7.4 预算匹配度判定规则

预算匹配度直接影响档位和排序。薪资配置表中每个服务类型对应两档价格（正常价区间 / 偏低价区间），预算落在哪档直接决定匹配等级。家政行业阿姨优先选预算高的客户，低预算客户匹配难度大，不应占用经纪人核心资源。

| 预算匹配等级      | 判定标准       | 对档位的影响              |
| ----------- | ---------- | ------------------- |
| **高匹配**     | 预算落在正常价区间内 | 进入 A/B 档打分，排序靠前     |
| **中匹配（偏低）** | 预算落在偏低价区间内 | 进入 A/B 档打分，排序靠后     |
| **严重偏离**    | 预算低于偏低价区间  | B-price 档，AI 培育不转人工 |

> 🎯 **预算口径 = 总价（总预算）**：此处"预算"即 §4.6 采集的总价（= 阿姨工资，无中介费差额），与报价、采集全链路同口径。**代码实况**：`leads/lead-grading.util.ts` 的 `parseBudgetNumber` 对 JSON 区间串**取上限 max** 与市场价比对（宁高勿低，故意偏松——预算 5000-6000 按 6000 判，避免误杀成 B-price）。  
> **市场价基准：** 以薪资配置表中对应服务类型 + 城市分级 + 面积的两档价格区间为准（正常价区间 / 偏低价区间）。

### 7.5 代码与 AI 分工边界

| 模块            | 交给谁    | 原因                                  |
| ------------- | ------ | ----------------------------------- |
| 预算匹配度判定       | **代码** | 查薪资配置表 + 比对价格区间，纯逻辑计算               |
| 时间紧迫度打分       | **代码** | 解析上岗时间字段，计算距今天数                     |
| 需求明确度计算       | **代码** | 统计有值字段数 / 总字段数                      |
| A/B 档三维度总分计算  | **代码** | 三项分数相加，纯算术                          |
| 线索分配（派给哪个经纪人） | **代码** | 城市 + 技能筛选 + 负载 + 成交率排序 + 超时转派，确定性规则 |
| C1 档情绪判断      | **AI** | 需理解语义、语气、上下文，非结构化输入                 |
| 需求采集对话        | **AI** | 自然语言交互，引导客户补充信息                     |
| B-price 类培育话术 | **AI** | 个性化沟通，推降维方案                         |

**核心原则：** 结构化输入 + 确定输出 = 代码；自然语言 + 模糊判断 = AI。

### 7.6 经纪人派单规则

#### 7.6.1 筛选条件（须同时满足才分配）

| 条件      | 字段                              | 说明                       |
| ------- | ------------------------------- | ------------------------ |
| 在线      | is_online = true                | 查 agent_sessions 表，离线不分配 |
| 同城市     | city = 线索.city                  | 严格匹配，不跨城市降级              |
| 擅长该服务类型 | service_types 包含线索.service_type | 数组包含判断                   |
| 未达最大负载  | active_leads_count < max_leads  | 手头线索不超上限（默认 10 条）        |

一个符合条件的都没有 → 线索标记 `pending`，等下一轮定时任务重试分配。

#### 7.6.2 Pending 状态说明

Pending（待分配）是线索在派单过程中的中间状态：线索已生成且符合分配条件，但暂时找不到合适经纪人，进入待分配池等待。**进入场景：** 所有经纪人都不在线 / 在线的无人擅长该服务类型 / 城市不匹配 / 所有符合条件的经纪人都已达最大负载。**重新尝试分配：** 有新经纪人上线（城市+技能匹配）/ 有经纪人完成接单负载下降 / 定时任务巡检补派 / 客户发新消息等业务事件触发检查。

#### 7.6.3 经纪人排序规则

符合条件的经纪人按优先级排序取第一个：**① 当前负载**（手头线索少的优先，active_leads_count 升序）→ **② 成交率**（负载相同时成交率高的优先，conversion_rate 降序）。核心逻辑：先让大家活均匀，活一样多的时候让好经纪人多接点。

#### 7.6.4 超时自动转派

分配给经纪人后，若在规定时间内没点「接单」（responded_at 为空），系统自动转派给下一个合适经纪人。

| 线索档位             | 超时时间 |
| ---------------- | ---- |
| A 档              | 2 分钟 |
| C1 档（情绪 = 高优先级）  | 2 分钟 |
| B 档              | 5 分钟 |
| C1 档（情绪 = 普通优先级） | 5 分钟 |

转派动作：旧经纪人负载减一 → 线索清空分配状态 → 重新走分配流程。定时任务每分钟检查一次。

#### 7.6.5 触发时机

线索进入 A/B/C1 档 → 调用分配 ｜ 经纪人点「接单」→ 标记已响应 ｜ 每分钟定时任务 → 检查超时转派 + 分配待分配线索。

#### 7.6.6 C1 高情绪加急兜底

C1 高情绪线索转人工时，若暂时没有匹配的在线经纪人，不能像普通线索一样进 pending 干等，需两层加急兜底。**第一层 AI 及时安抚：** C1 高情绪线索进入 `pending_high` 状态时，立刻触发 AI 发一条安抚消息（话术参考"非常理解您的心情，已为您加急安排专属顾问，稍后就会主动联系您，请稍等~"）；用 `pending_comfort_at` 记录安抚发送时间，同一 pending 周期只发一次防重复骚扰。**第二层高优先级 Pending + 优先分配：** pending 分两档——`pending_high`（高优先级，C1 高情绪）和 `pending`（普通优先级）；补派时先分配所有 pending_high（按进入时间先进先出），再分配普通 pending。

#### 7.6.7 C1 同一经纪人跟到底

C1 线索经历「转人工 → 交回 AI 采集 → 升级 B/A 档 → 再派单」完整流程。升级后强制分配给第一次对接的经纪人，同一个人跟到底。**核心规则：** leads 表新增 `original_agent_id` 记录第一次分配的经纪人 ID；C1 升级到 B/A 档重新派单时优先检查原经纪人（在线 + 同城市 + 擅长该服务类型）→ 直接分配；**不受负载上限限制**（即使 `active_leads_count >= max_leads` 也强制分配）；客户主动转接经纪人时 `original_agent_id` 更新为新经纪人。**经纪人下线提示：** 下线时检查是否还有跟进中的线索，有则返回提示"您当前还有客户在跟进状态中，确定要下线吗？"，不强制阻止，经纪人确认后可正常下线（force=true）。

#### 7.6.8 派单实时性机制（混合模式）

妙搭平台定时触发器最小间隔 30 分钟，无法做到分钟级超时检查。采用「**定时兜底 + 业务事件实时触发**」混合模式。

**三层触发机制：** **业务事件触发（主力）**——在 3 个关键节点顺带调用超时检查 + pending 补派：① 新线索进入 A/B/C1 档 ② 经纪人上线 ③ 客户发新消息（AI 对话入口）。**防抖保护：** 业务事件触发加 1 分钟最小间隔，避免频繁触发全量检查；异步执行（`void`），不阻塞主流程。**定时任务兜底：** 每 30 分钟执行一次全量检查，确保系统静默时也能运转。

**效果预期：** A 档 / C1 高情绪（2 分钟超时）：通常 2~~3 分钟内转派；B 档 / C1 普通情绪（5 分钟超时）：通常 5~~6 分钟内转派；系统完全静默时：最多 30 分钟（兜底）。

### 7.7 整体判定流程

```
线索进来
  │
  ├─ 命中黑名单 → D 档（不分配）
  │
  ├─ AI 走完采集流程？
  │   ├─ 是 → 计算预算匹配度
  │   │     ├─ 严重偏离 → B-price 档（AI 培育，不转人工）
  │   │     └─ ≥偏低价区间 → 三维度打分
  │   │           ├─ ≥6 分 → A 档（2 分钟响应）
  │   │           └─ <6 分 → B 档（5 分钟响应）
  │   │
  │   └─ 否 → 客户主动转人工？
  │         ├─ 是 → C1 档（按 7.3 情绪分级，对应响应时限）
  │         └─ 否 → C2 档，AI 继续采集
```
